# R11 数据集用途分层与受限评测集方案

日期：2026-11-09（Asia/Shanghai）。状态：**待负责人确认，仅调研和设计，尚未实施分层或迁移真实数据。** 用户已直接授权的字段“是否导出”、版本恢复及合成ZIP下载验收由本轮其他实施记录负责；本提案不把这些实现等同于已经支持分层发布。

## 建议与需要确认的一点

按目前描述的跨团队工作方式，建议采用**一份受限主库维护样本，通过管理字段定义用途，发布时生成四个固定视图**。算法和QA团队下载明确共享的产物，不获得包含隐藏样本的主库读取权。不要人工维护三份互相复制的数据文件。

如果算法或QA也需要进入主项目浏览、检索、编辑源样本，则把隐藏集放入**独立私有项目**。在当前权限结构下，同一个项目中的`hidden=true`、隐藏标签、分支或单独文件，都不能阻止有项目读取权的人从原文件、历史提交或附件中取得隐藏样本。

需要确认的是：**算法/QA仅消费发布文件，还是也需要进入主库协作？** 推荐先采用“只消费发布文件”的方式；如果实际需要主库协作，则采用共享项目＋独立隐藏项目。两者均只扩展TypeScript Web/BFF，不修改Oxen内核。

## 业界模式与本项目推论

| 已核对的一手资料 | 事实 | 本项目采用的设计判断 |
| --- | --- | --- |
| [Hugging Face文件与splits](https://huggingface.co/docs/hub/datasets-file-names-and-splits) | 数据集可以用明确的文件/目录映射表示多个命名split | 对外提供命名JSONL；物理导出文件不必等于日常维护的主表 |
| [MLCommons AILuminate FAQ](https://mlcommons.org/ailuminate/safety-faq/) | 区分用于内部迭代的practice测试与使用完整隐藏题目和私有评估器的official测试 | 共享测试集与受限最终评测集分开分发；隐藏性依赖接收者范围，不依赖字段名称 |
| [HumanSignal ground truth说明](https://docs.humansignal.com/guide/ground_truths) | ground truth是经过核实的高质量正确答案；该产品页面功能属于Enterprise | “金标”表达质量和裁定可信度，不能只把任意一行勾选为gold就视为已经核准；这里只借鉴语义，不声称社区版提供该功能 |

以上是已公开产品/文档事实。下文的字段ID、UI、权限与产物组织是适配现有Oxen Web的本地设计，并非上述工具共同规定的标准。

## 三个概念分别表示什么

**金标**：人工核准、解释充分、覆盖关键类别的精选用例，供算法先检查基本能力。样本必须保持当前正文、源真值与人工采纳结论的区别，并通过现有独立复核。金标不等于“所有安全风险均有统计代表性”。

**回归**：已发现缺陷、重要边界和历史失败场景，供QA/自测反复运行。它是用途，一条高质量样本可以同时属于金标与回归集。

**隐藏**：对算法和普通测试消费者尚未公开的独立评测范围。它是暴露与权限边界，并不是一种标签质量。隐藏样本内部也可以有核准的高质量真值，但默认不进入对外金标或回归产物。

因此不建议做互斥单选`gold | regression | hidden`。建议把“使用范围”和“用途”拆开：先决定是否允许共享，再决定共享样本属于哪些测试套件。曾经向算法团队共享的样本，不能通过重新勾选“隐藏”恢复成未见过的独立留出集。

## 源数据如何组织

| 方案 | 适用条件 | 成本与局限 | 建议 |
| --- | --- | --- | --- |
| 一个项目手工维护gold/regression/hidden三个文件 | 仅管理员保管且规模很小 | 重复内容、标签和修正容易漂移；当前项目只配置一份`canonicalPath`，会重新引入切物理文件的操作；同repo不提供隐藏权限 | 不作为默认日常维护方式 |
| 一份受限主库＋用途管理字段＋固定导出视图 | 算法/QA只接收发布文件；可信标注/复核人员可读主库 | 维护量最小；必须对共享ZIP及辅助文件做完整裁剪，分享对象要明确 | **默认建议** |
| 共享主项目＋独立隐藏私有项目 | 算法/QA需要主库read或参与编辑 | 复用现有项目范围权限；需要关联两个固定commit和版本，不是原生单commit原子事务 | 入库协作时建议 |
| 同一可共享项目内增加真正的行/列级隐藏权限 | 强制一项目、部分成员可读部分行 | 必须保护原件、历史、diff、统计、查询、ZIP、导出及所有通用文件入口；单改列表过滤远远不够 | 本轮不建议，改造和回归成本最高 |

默认方式中，每个样本只维护一个规范内容和稳定身份。导出JSONL是固定版本的投影视图；修改后通过新提交、新Release产生新产物，不手工同步多份副本。Skill仍是“一条样本关联一个惰性ZIP”，不展开执行。

团队隔离以实际部署为前提：R10当前本机仍保留开发者owner兼容入口，不能把该模式当作多人保密。落地本方案时需启用`BFF_TEAM_MODE=true`、独立受限身份并保护官方上游，沿用[身份权限说明](../access-and-audit-r10.md)与[运行手册](../operations-runbook.md)；只给算法团队一个看起来不同的项目名并不建立隔离。

### 现有工程事实

- `packages/shared/src/dataset.ts`中的`DatasetDescriptor`通过一个`canonicalPath`表示项目的逻辑样本入口；UI按分支读取这份完整逻辑集。
- `apps/server/src/repository-access.ts`的读取权限和凭据scope以项目为界；现有任务的行范围约束写入/任务协作，不构成对项目raw或历史文件的行级保密。
- `apps/server/src/releases.ts`从固定主线提交构建，正式发布检查独立复核；当前没有四套用途筛选/多产物规则。
- 当前`StoredShare`实际包含`assetId`，`share()`自动绑定该Release中首个ZIP，`sharedDownload()`只返回该绑定资产。**分享不是对所有资产的任意读取，但目前也没有供用户选择分层资产的安全交互。** 新方案需要明确选定共享包，不能依赖资产数组顺序碰巧正确。
- 标准ZIP还包含标签、意见/复核证据、附件映射、README和provenance，且可选打包原始归档。仅过滤`samples.jsonl`不能证明隐藏内容已经被排除。

## 建议的管理字段

发布分组属于项目维护信息，和风险分类、恶意/正常判断分开。建议按稳定样本ID保存版本化BFF扩展，在数据编辑中呈现为可筛选的管理列；负责人通过专门操作维护，普通标注人员可读但不自行改变发布边界。下列ID为本地建议，尚未创建字段或修改源记录。

| ID／显示名 | 类型、选项 | 规则 |
| --- | --- | --- |
| `evaluation_visibility`／使用范围 | 单选：`shared`可共享、`holdout`受限隐藏；另保留未设置状态 | 新导入默认未设置，不自动共享；未设置条目不进入任何正式导出视图。只有负责人可修改，并产生提交与宏观审计 |
| `evaluation_suites`／测试用途 | 多选：`gold`金标、`regression`回归；默认空 | 可同时选择。共享且未加入两套精选集的样本仍可进入“非隐藏全量”；gold必须通过现有独立复核和明确采纳 |
| `family_id`／关联家族 | 可选字符串 | 同一攻击模板、同一原Skill包的变体、同一敏感实体生成族应使用同一组。已知同族必须共同处于共享或隐藏范围；未知族需人工检查，不能宣称完成语义去重 |

不额外新增一套`review_status`或把“gold”当作新的审核状态，继续消费现有提交指纹和复核证据。模板维护者决定领域解释，项目负责人决定哪些已复核条目进入用途套件，标注人员继续处理正文和风险标签。

这些管理字段可以不随样本导出；筛选先读取固定版本的管理信息，再应用本轮新增的“是否导出”字段投影。未导出一个管理列，不会改变它的筛选结果。字段不导出也不等于该字段对主库成员保密。

## 四份产物与去重规则

下表的`已核准`指通过现有正式Release校验，且复核指纹与当前正文、附件和规范一致。四个视图使用同一固定源版本；两库方式则记录两个固定源版本。

| 产物 | 集合定义 | 接收者／使用时点 |
| --- | --- | --- |
| `gold.jsonl` | 已核准 ∩ `visibility=shared` ∩ `suites`含`gold` | 算法先测精选基线 |
| `regression.jsonl` | 已核准 ∩ `visibility=shared` ∩ `suites`含`regression` | QA及算法日常自测 |
| `nonhidden-all.jsonl` | 已核准 ∩ `visibility=shared` | 正式候选前的共享全量；包含上述两集和其他共享样本 |
| `hidden.jsonl` | 已核准 ∩ `visibility=holdout` | 安全评测负责人在模型、提示词、规则与依赖版本冻结后作最终独立评测 |

金标与回归可以重叠，`nonhidden-all`是按稳定ID去重后的共享全集，不是把两个文件简单拼接。隐藏与所有共享产物必须无交集，且已知`family_id`也不能跨共享/隐藏边界。未设置范围或未核准的条目在构建预览中给出数量和原因，不偷偷归入共享全量。

“非隐藏全量”按此方案指**允许交付且已核准的全部共享样本**，不包含未审核、范围未定或被隔离的原始记录。若负责人希望另有内部未审核工作快照，沿用现有工作快照，不能将其作为正式四产物之一冒充审核通过。

### ZIP与分享边界

默认分为两个资产包：

```text
benchmark-vX-shared.zip
  gold.jsonl
  regression.jsonl
  nonhidden-all.jsonl
  selected-attachments/
  README.md + manifest.json + checksums.sha256

benchmark-vX-hidden.zip              # 仅授权评测人员可取得
  hidden.jsonl
  selected-attachments/
  README.md + manifest.json + checksums.sha256
```

共享包不含隐藏包、不含隐藏成员清单和隐藏资产引用。分享操作显式选择“共享测试包”，显示包含三个文件及其条数；隐藏包默认禁止匿名/普通外链分享。单库方式可采用分开的发布记录保持权限明确；若采用一个逻辑Release页展示两个包，必须在BFF逐资产授权与资产列表过滤，不能只隐藏按钮。

现有整个原始输入ZIP可能同时包含共享和隐藏记录，分层交付默认不附带该原始归档。`labels.json`、fine annotations、review证据、provenance、反馈、附件映射和README都必须按该资产允许的稳定ID裁剪并检查引用；保留源归档仍可在受限主库中进行。Skill附件只有被对应视图引用时才进入该包，同一ZIP在一个包内去重，按SHA校验、不执行。

## UI原型

```text
项目设置 → 发布分组
  协作模式：受限主库 / 共享库＋关联隐藏私库（管理员）
  管理列：使用范围、测试用途、关联家族
  范围未设置：N条          [进入筛选]

数据编辑
  [使用范围 ▼] [测试用途 ▼] [复核状态 ▼]
  序号 | 内容字段… | 使用范围 | 测试用途 | family_id
  负责人：[批量设置分组] → 预览影响条数 → 保存私有草稿 → 明确提交
  标注人员：分组只读，正常编辑正文/标签与提交复核

Releases → 新建候选
  固定源版本：main@<commit>
  导出视图：☑ 金标 ☑ 回归 ☑ 非隐藏全量    受限：☑ 隐藏
  每份：条数、附件数、包含字段、排除/阻止原因
  [核对成员变化与重叠] → [构建] → [核对资产] → [发布]
  算法/QA的分享页只提供共享包；评测人员看到其获准的隐藏包
```

沿用现有加载、空集、失败、草稿恢复和明确提交交互。空金标/回归集合不能显示成“已覆盖”，预览明确0条；同一版本已发布后成员变化通过新版本表达。用户不再选择`data/`或手工切换三个物理文件。

## 发布冻结与复核

发布清单固定项目/commit、分组规则版本、已导出字段清单、稳定样本ID集合摘要、附件SHA、独立复核摘要及每个产物SHA。共享清单只描述共享成员，受限清单保留完整评测信息。两库方式同时固定两个commit，任一源版本、成员范围、字段规则或审核指纹变化都要求重新构建和确认；不依赖两个分支“恰好同时是最新”。

分组变化不自动赋予样本新的正确答案，但会改变评测集组成，必须产生版本与发布差异。当前复核是否可沿用要按实际字段语义核验：正文/真值/附件/规范有变沿用现有失效规则，纯用途变化不伪造新的专家裁定；候选资产指纹仍必须变化。所有分组调整由服务端检查负责人权限、当前HEAD及expectedCommit，不能靠前端只读阻止越权。

隐藏测试建议由评测负责人运行，算法团队提交冻结的模型或系统配置，接收约定的汇总结果。直接开放全部逐例答案、反复根据隐藏集调参，会逐渐削弱留出意义；某批样本已暴露后，可以转入共享回归并补入新的未暴露隐藏样本，用新版本记录，不能声称“隐藏一次测试即可证明没有过拟合”。此流程借鉴独立评测原则，并不保证检测所有形式的污染或过拟合。

## 实施量和验收

以下为基于现有Web/BFF结构的工程估算，不是已实施工时或上线承诺，不包含对四类真实样本进行人工分组/专家复核的工作量。

| 工作 | 估算人日 |
| --- | ---: |
| 版本化分组、负责人权限、工作台筛选/批量编辑及草稿/CAS | 2–3 |
| 四视图构建、辅助文件裁剪、附件去重、可复现清单 | 2–3 |
| 共享/隐藏资产列表与下载授权、发布预览和份数展示 | 1–2 |
| 负向权限、往返、发布失效、UI与故障回归 | 2–3 |
| 默认受限主库方式合计 | **7–11** |
| 若需共享主库＋关联隐藏项目：双源固定版本、来源一致性及UI关联 | 额外2–4 |

同repo真正行级保密需另行审计所有通用原件/历史入口，不能沿用以上工时；不建议为本需求先实施该路径。

验收必须包括：

1. 用合成样本验证四集合精确成员、gold/regression可重叠、共享全集去重、共享与隐藏的ID/已知family无交集；未设置范围/未核准条目不进入正式包。
2. 源记录、独立意见、核准结论和用途字段各有来源；只有负责人能改分组，普通标注的HTTP直调也拒绝越权，修改失败保留草稿且不产生提交。
3. 固定commit重复构建得到相同成员与内容校验；分支推进或分组/导出列改变不会覆盖既有Release，候选指纹与差异可核对。
4. “是否导出”取消字段在每份样本文件均不存在；系统操作时间和操作人继续不进入样本文件；筛选所需的管理列即使不导出仍正确分组。
5. 共享ZIP的所有内容、标签/意见、provenance、原包及附件引用都不含隐藏内容；隐藏资产ID/路径、分享、下载、历史读取的负向权限实际测试，不以按钮不可见为通过。
6. 对一条Skill样本验证ZIP按字节保留及SHA一致，多视图仅按引用纳入，不安装或执行；文本/JSONL/ZIP范围保持，不新增多媒体样本功能。
7. 失效分享、错误源HEAD、权限中途撤销、构建失败/结果未知保留真实状态与输入，不自动重复提交或默认降级到全量导出。
8. 主库仅由可信团队读取的部署前提明确；如算法/QA有主库read，必须选择独立隐藏私库方案后才能称“对该团队隐藏”。

确认协作方式和上述四份产物语义后，再创建分层实施任务。本次未创建分层字段、修改成员权限、搬迁样本或构建分层Release；没有新增SaaS登录后观察。

## R12 决策追记（2026-11-09）

用户已确认“算法团队和 QA 只下载发布包测试”。据此批准实施默认方案：一份受限私有主库、版本化分组管理信息、共享测试包及独立受限隐藏包。上述“尚未实施”保留为R11提案当时的事实，R12的实际实现与验收以[实施记录](../implementation-r12.md)为准。
