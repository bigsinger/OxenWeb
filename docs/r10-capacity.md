# R10 四用户容量与并发验收

范围：S05/S06，官方 Oxen 0.67、单活动 TypeScript BFF。只运行隔离的合成服务，不修改 Oxen 内核，不读写四个真实 benchmark 正文或角色，不停止正式3001/3002。

## 可复现入口

`node --import tsx scripts/r10-capacity-acceptance.ts --smoke` 执行独立合成准备与60秒冒烟，**不能当作正式容量通过**。不加 `--smoke` 时，执行三轮各30分钟的真实经过时间；每轮结束后还有30秒空闲收敛及5次内存采样。不得修改系统时间、缩短计时、取消权限校验或把不同短测相加冒充三轮。

脚本在 `3008` 启动项目持有的官方二进制，存储位于专属 `r10-capacity-*` 原生目录；在 `3009` 启动独立 Node 子进程 BFF，并实际调用 `acquireInstanceLease` 与 `InstanceRuntime`。BFF进程独立于负载驱动，内存指标不混入驱动准备数据所需的内存。两者在结束时核对归属并受控关闭；不使用生产端口，不盲目按进程名杀进程。

`--run-id=r10-capacity-...` 可重新运行某个明确命名的合成夹具，仍必须重新通过源字节、行数和包数量核对。正式验收前使用已冻结的实际源码；重新运行失败场景必须保留之前结果，不能覆盖为通过。输出仅写 `.data/r10-capacity/`，不含原样本内容、明文令牌或签名下载地址。

## 四用户配方

3位独立 editor（可编辑及标注）与1位独立 reviewer，使用各自稳定 actor ID、各项目受限凭据与分配的任务分支。令牌只驻留负载驱动内存，BFF凭据存储保留哈希。每个项目分配3个不重叠、各10条的固定任务范围；普通查询仍浏览完整的对应数据集。每轮使用相同的约10分钟轮换节奏跨项目工作，复核者按固定任务提交读取证据；不以每轮更换数据配方掩盖内存变化。

- 每位用户约每15秒发起一组正常操作，四用户同时活动。分页、全表数字过滤、全表升降序轮换；排序、过滤先于分页。
- 每位 editor 每8个循环（约2分钟）修改其任务中的10条内容及标签，保存合法私有草稿并明确一次提交，再提交给独立复核者。
- 复核者读取任务、固定样本证据和按操作时间排序的列表，并在执行者完成提交之后写入复核。对同一任务分支遵守真实的交接顺序；复核写入期间执行者继续只读，其他分支和其他用户仍正常读写。版本竞争另由CAS和故障回归覆盖，不靠丢弃过期草稿来制造“顺畅”结果。
- 每5分钟最多一个重操作与用户读取并行：10条JSONL追加导入的检查/预览/确认、两个固定 ZIP 版本的包内差异、工作快照构建及实际资产下载SHA核对，轮换执行。快照不冒充经过完整复核的正式Release。
- 重操作只允许一个活动实例。HTTP/队列的429、合法CAS409单独计数；意外5xx、请求超时、语义校验或未处理草稿问题不能被算成成功。

合成准备、账号与任务配置不计入负载窗口。冒烟的用户节奏与正式相同，只把重操作间隔缩短以便快速发现路径错误；短测分位数不足以证明正式门槛。

## 门槛与测量

记录平台/Node/CPU/可见逻辑核/总可用内存、固定数据字节、每类请求数量和节奏、BFF PID、开始结束时间、每轮实际经过时间。请求耗时包含客户端等待完整HTTP响应与JSON解析，不扣除认证、权限、排队或全表扫描。

普通分页、全表筛选/排序、合法私有草稿保存与草稿查询为建议目标集合：P95≤2秒、P99≤5秒。实际正式提交、任务/证据/复核与重操作另列分位数，不能混入更快请求隐藏长尾；所有类别都要求意外5xx和非预期超时为0。完成账号/任务设置后会受控重启独立BFF，让正式第一批请求包含真实冷启动，不把准备阶段缓存冒充冷请求；首次12个目标请求另外报告，并继续留在整体P95/P99中。

三轮各自的普通目标请求集合也必须分别满足同一P95/P99门槛，不能用其他轮的更快结果稀释一轮失败；完整90分钟汇总仍单独报告。首轮的真实BFF冷请求保留在首轮与总集合中，目标和业务配方不变。

BFF峰值RSS目标≤1.5GiB，优先采用进程OS累计峰值并持续采样。每轮空闲后取5次RSS中位数；第三轮相对第一轮增长≤10%，允许64MiB测量噪声，即增加量不得超过二者较大值。测试不主动强制GC，不用缩短数据、取消附件或提高内存预算来改变结果。

正式报告为 `.data/r10-capacity/<run-id>/formal-verification.json`；运行进度为 `formal-progress.json`。同时保存带execution ID的不可覆盖报告与请求元数据日志，保留每一次运行。字段包括模式、三轮时长、每类计数/分位、预期状态、错误、原生与BFF位置、数据体量、内存和结果。记录开始/结束时后端、共享契约及验收脚本源码SHA；过程中源码变化会拒绝正式通过。只有三轮达到实际30分钟、全部正确性与目标都符合，才会写 `passed:true`。

## 已发现并处理的初次诊断

第一次60秒冒烟 `r10-capacity-mw7xf9l4` 如实失败：测试驱动让复核者与执行者同时写同一任务分支，CAS拒绝后留下了过期草稿，后续请求不能继续。保留该结果，不把冲突报成“通过”。驱动改为提交→复核的明确交接，仍保持四用户、分支间写入及读取并行。

该次普通请求P95约2251ms/P99约6144ms，合法草稿保存长尾约10秒，BFF峰值约1.13GiB；它与完整重回归并发，且旧冒烟的提交节奏比实际配方密集，不能据此推断正式容量已经达标。进一步定位发现每条operation在三个阶段重复读取权限/任务上下文。经主任务批准，将每个阶段按操作类型/范围/路径成组，传完整操作与样本ID并集；保留计划前、计划后、实际提交前的权限、任务和HEAD再核对，无跨请求权限缓存。新增回归验证全范围、提交前撤销和自定义authorizer不同操作语义，不以放宽权限换取性能。

之后按提交→复核交接和真实15秒节奏的冒烟，已无错误，但草稿冷路径仍有约5.53秒长尾。经批准，计划预览进一步复用同一固定提交已验证的原表解析、原身份和原哈希，避免为overlay重复读取/解析/哈希整份36MB源文件。证据用WeakMap附着于现有快照生命周期，原始行引用与原快照共享；不保留额外raw Buffer，不缓存权限、操作者计划或可变返回对象。新HEAD/路径重新物化，所有三阶段权限和CAS保留。53项相关回归通过，包含冷原表只读1次、actor隔离、调用方修改返回对象不污染证据、新HEAD拒绝旧基点、导出和私有草稿等。

复用后的60秒真实冷启动冒烟无5xx、超时或语义错误；22个目标请求P95约3894ms/P99约4459ms，其中首次12个冷窗口最大约4459ms，3次合法草稿保存最大约3117ms。BFF峰值约1.058GB、空闲约445MB。短窗口冷请求占比高，不能以它声称正式P95达标，也未去除这些冷样本；随后继续执行下文记录的完整三轮窗口。

主任务在运行中发现另一个真实故障边界：客户端断开连接时，handler可能仍等待官方写入，而旧代码已释放容量/排空租约。因此在完成修复前中止本轮，**未完成，不通过**。最后持久化进度为691156ms、224个目标请求，P95约1967ms、P99约3371ms，BFF峰值1132113920B，未出现意外5xx、超时或语义错误；这些数值不能代替完整验收，也不能计入之后的90分钟。

验收驱动随后补充逐请求独占append-only日志，且增加 `--stop --run-id=<当前run-id>` 的execution专属取消请求。取消不获取或暴露令牌：运行中的驱动让当前操作完成，再通过现有鉴权关闭入口排空BFF，最后核对归属并停止隔离原生服务。取消报告包含`interrupted`且`passed:false`，不将部分轮次算成通过。正常SIGINT/SIGTERM也使用同一收尾路径；Windows不能投递优雅信号时使用上述文件请求，不依赖强杀。

### 保留的可选性能设计（尚未实施）

只读诊断发现固定提交快照缓存仅4项，四个项目的多个任务分支、复核与快照读取会导致淘汰；新HEAD需要重新物化。不能仅按路径或修改时间把不同版本当成相同文件，也不能跨请求缓存权限、actor计划或CAS结果。

若完整实测确实超过目标，可先评估官方契约中的 `GET /api/repos/{namespace}/{repo_name}/meta/{resource}`。它在固定commit下返回文件`hash`、`size`以及`resource`的commit/path/version。隔离合成文件的只读响应已证实这些字段可用，36MB规范文件hash为Oxen原生128位值，不应称为SHA256。候选设计是严格核对固定commit/path与非目录身份后，按服务authority、仓库、规范路径、原生hash、字节数和解析格式复用不可变原始行；首读仍保留真实字节SHA256。每个HEAD的descriptor、身份映射、字段规则、覆盖记录、标签与授权独立加载，不能顺便复用它们。任何元数据缺失都回退原始读取，且应有保守字节预算、淘汰与压力回归。相较直接扩大完整快照数量，这样可减少大表重复解析与内存副本。该方案未应用于已记录的正式或冒烟测量。
