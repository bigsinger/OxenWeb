# R11 恢复数据版本（新增提交）

本地扩展，2026-11-09。复用冻结的提交历史、固定版本、文件差异和明确确认交互；没有新增SaaS观察，没有修改Oxen内核、固定OpenAPI或原生存储格式。

## 使用方式与边界

在项目“版本与合并 → 提交历史”打开历史提交，项目管理员可选择“恢复到此版本（新增提交）”。先读取完整文件树并核对变更文件，填写提交说明，输入`namespace/project@branch`后才可创建恢复提交。

- 恢复的是所选固定提交的文件和数据快照，不是仅逆转该提交的单个补丁。所选历史提交、后续已有提交和分支历史都保留；新的提交以当前分支HEAD为父提交，不执行reset、强制推送或删除历史。
- 源文件、样本覆盖记录、稳定身份、标签、采用的固定模板与字段配置随目标快照恢复；目标中不存在的当前文件暂存删除，目标新增或变化的文件按原始字节恢复，包含ZIP。ZIP只保存和校验，不安装、不执行。
- 当前`.oxenweb/repository.json`整份保留，因此项目显示名称、简介、可见性、默认分支和成员权限不回到旧值。组织治理字典、凭据、宏观日志、任务分配和私有输入属于BFF控制面，不随数据快照回滚。
- 当前分支的历史复核证明文件会从新快照移除。恢复不是自动通过复核；正式Release仍需针对恢复结果重新建立有效独立复核。
- 本人有未提交样本草稿或项目有活动标注任务时拒绝恢复，并保留输入。其他人员的私有草稿和原工作区不被删除，原基点仍可核对；旧基点不能静默覆盖新版本。
- 已是当前HEAD的版本直接提示无需恢复；预览后分支变化、权限被撤销、预览哈希变化均拒绝提交。

“最后修改时间/操作人”保持操作证据语义：实际恢复了内容、样本判断或关联附件的条目记录本次操作者及当前时间；未变化条目保留当前证据，原`source-file`粗粒度或`unknown`不会升级为精确Web操作。创建/导入时间沿用已有可靠证据，不伪造历史人员。活动文档新增可选`source`证据类别，旧Web写入文档没有该字段时仍按既有Web记录处理。

## 实现与保护

本地BFF接口：`POST /api/repos/:namespace/:repo/history/restore/preview`和`POST .../history/restore`。共享DTO统一`RepositoryVersionRestore*`，避免与项目回收恢复同名。

官方能力仅使用固定契约已有的目录分页、固定提交文件读取、workspace写入/合并，以及`DELETE .../workspaces/{workspace_id}/files`暂存删除、`GET .../workspaces/{workspace_id}/files/{path}`读取原始暂存字节。目录重复、越界、非直接子项或不完整分页均失败；删除接口不是完整200结果时拒绝提交，不接受部分恢复。

恢复workspace从创建时就使用保留的`oxenweb-restore-`原生名称前缀，不依赖有崩溃窗口的临时内存登记。所有通用HTTP工作区写入、上传、提交和删除都拒绝这一类工作区，包含所有者；通用创建也不能借用该前缀。因此BFF重建后，未知结果的暂存现场仍然隔离。受管上游应继续按运行手册隔离，不能让不受BFF控制的人员直接改原生工作区。

提交前及Provider提交串行队列内再次核对权限、分支HEAD、完整暂存路径/状态和每个非删除文件的原始字节。只有路径相同、状态相同而正文被改过时也会拒绝。写入租约由实际handler结束释放；整仓预览/恢复进入现有单重任务预算，保留429保护。

恢复提交沿用持久operation ID、真实提交marker和预期父节点，宏观事件为`project.version_restored`。真实提交完成而回复丢失时，不自动再提交；可按固定标记核对原结果。同ID重试不会产生第二个提交。界面未知结果后锁定再次提交，自定义说明、目标与基点仍留原页；“在新页打开操作核对”不会卸载恢复面板。关闭/刷新原页不提供新的恢复表单检查点承诺。

支持预算为每个版本最多50000个目录/文件、目录64层、累计256MiB；单文件仍遵守既有raw代理限制（JSONL/NDJSON64MiB，其他25MiB），生成活动记录最多8MiB。超过预算在写入前拒绝，不返回部分恢复。大仓库仍需受控CLI流程。
