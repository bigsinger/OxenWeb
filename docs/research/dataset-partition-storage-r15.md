# 分层数据的项目、成员映射与发布方式 R15

核对日期：2026-11-09，Asia/Shanghai。本文只解释现有本地TypeScript Web/BFF扩展及公开一手实践，不修改真实数据、项目权限、服务或Oxen内核；没有新增SaaS观察，也没有把R14只读候选写成已实施分组。

## 当前项目采用的方案

**每个现有数据集项目保留一份受限私有主库，在同项目内用版本化的评测管理信息关联样本，再按固定版本生成不同发布视图。** 当前四类领域仍是四个项目，不是把四类合成一个大项目；也没有为每类再复制出金标、回归、隐藏三个可编辑项目。

概念上是给样本设置分组字段，但它们不放入源JSONL，也不作为标注人员维护的普通“人工标签”。`packages/shared/src/evaluation.ts`和`apps/server/src/dataset-evaluation.ts`定义了独立的评测管理层，按稳定`rowId`保存于`.oxenweb/dataset/evaluation.json`：

| 管理信息 | 作用 | 关系 |
| --- | --- | --- |
| `visibility`：未分类／shared／holdout | 决定是否纳入外部共享范围 | 三者互斥；未分类不自动共享 |
| `suites`：gold／regression数组 | 决定哪些已核准共享条目进入评测套件 | 可重叠；不是互斥的三分类 |
| `familyId` | 记录已核准的原题、原包或变体关联组 | 已知同族不得跨共享与隐藏；不能凭空声明语义去重完成 |

源真值回答“原数据怎么定义”，人工标签回答“标注／审核人员如何判断”，评测管理信息回答“这条样本给谁、用于哪份发布”。三者分别存储；普通标注者不因可打标签就获得修改共享／隐藏范围的权限，当前分组修改要求发布负责人同时具备`release.manage`和`data.edit`。

例如，一条合成样本可以属于shared，同时用于gold和regression。隐藏样本也需要高质量真值和独立复核，但共享`gold.jsonl`只选取shared中的gold用途成员，不会因为隐藏样本质量高就把它带进共享金标包。勾选gold用途本身不会生成专家认可或审核证明。

## 分支、版本和导出不是同一个维度

| 机制 | 本项目用途 | 不应承担的职责 |
| --- | --- | --- |
| Oxen分支 | 多人编辑／标注、任务隔离、复核、合并 | 不将gold／regression／holdout长期做成三条“保密分支” |
| 分组映射 | 在同一已提交快照中表达样本成员范围与用途 | 不把普通行字段当作仓库权限 |
| Release | 冻结源提交、字段投影、规则／复核和附件成员，交付不可变文件 | 不在每次下载时对可变main临时筛选出不同内容 |
| 项目／仓库权限 | 确定谁能读主库、原文件和历史 | 不假设隐藏一个表格列就能阻止读取源数据 |

分组修改沿用本人私有草稿、差异核对和一次明确提交。发布从固定Oxen提交构建，后来继续编辑不会改写旧Release资产。归档、源表和辅助元数据不能绕过成员边界进入共享包；字段投影仍遵循“是否导出”，系统操作人／时间不作为样本数据列混入。

现有`apps/server/src/tiered-release.ts`和[分层发布契约](../r12-tiered-release.md)生成四份JSONL视图：

| 文件／包 | 内容与对象 |
| --- | --- |
| `gold.jsonl` | 明确shared、具有有效独立复核、用途含gold的成员 |
| `regression.jsonl` | 明确shared、具有有效独立复核、用途含regression的成员 |
| `nonhidden-all.jsonl` | 全部已核准shared成员，含金标、回归及其他可共享样本，以稳定ID去重 |
| `hidden.jsonl` | 已核准holdout成员，独立隐藏资产，只供有权评测／发布负责人 |
| 共享ZIP | 前三份JSONL及其对应附件／裁剪后的辅助信息；外部分享明确绑定这一资产 |
| 隐藏ZIP | 隐藏JSONL及对应文件，逐资产鉴权，不使用普通共享令牌分发 |

“分享／共享全集”是交付范围，不是与金标、回归并列、互斥的第四份可编辑母本。金标和回归交叠是有意允许的，不能把两个结果当作彼此独立的留出实验。未分类、未有效复核条目排除并计数，不悄悄算入非隐藏全集。

## 一个项目还是多个项目

| 场景 | 建议形式 | 理由／代价 |
| --- | --- | --- |
| 当前：可信维护人员管理主库，算法与QA只下载发布包 | 每类项目一份受限私有主库＋成员映射＋固定Release视图 | 一份正文、标注、来源和历史；修订无需在三份可编辑副本间同步；外部只拿获准资产 |
| 算法／QA需要登录浏览或编辑共享样本，但不能看到隐藏输入 | 共享项目与独立私有隐藏项目／存储分开，使用受控成员清单关联 | 仓库read通常可读原文件及历史；字段和分支不提供同仓库的行级保密；需承担跨项目身份、去重、版本和发布对账 |
| 不同法律／来源许可、保留周期、负责人或运维边界 | 按治理边界分项目，必要时跨库登记族与发布成员 | 分开的理由是访问／生命周期，不是仅因成员有不同用途 |
| 只为方便下载而建立gold／regression／hidden三份可编辑项目 | 当前不建议 | 重复维护正文和标注、容易版本漂移；gold／regression可交叠时尤其难同步 |

对当前已确认的“算法／QA只下载包”方式，继续使用第一行更合适。若协作方式改变，应先调整主库访问边界；只改行的holdout值不能收回已有原件、历史、外发副本或已曝光内容。受限主库仍须保护上游凭据与磁盘，BFF分组不能阻止绕过BFF直接读取上游的人。

## 一手实践支持的原则

没有在下列一手资料中发现“金标／回归／隐藏必须拆成几个仓库”的统一规定。应将逻辑成员、交付文件和访问权限分别设计，仓库数量取决于实际治理边界；这是结合本项目条件作出的架构判断。

| 一手来源（2026-11-09核对） | 该来源直接支持的事实 | 对本项目的推论 |
| --- | --- | --- |
| [Hugging Face：File names and splits](https://huggingface.co/docs/hub/datasets-file-names-and-splits) | 一个dataset repository内可以用文件名、目录及自定义split组织多个数据划分；一个split也可跨多个文件 | 逻辑划分不要求每份都建独立项目。HF的train／validation／test示例不等于我们的gold／regression应互斥，更不证明同仓库split有独立保密权限 |
| [MLCommons：AILuminate Safety](https://mlcommons.org/ailuminate/safety/) | Practice用于迭代；Official使用保密的正式测试提示；结果绑定基准与评测版本标签 | 把可见迭代数据与正式隐藏评测的访问和报告边界分开。它不规定我们的私有主库存储位置，也不为任意自有候选提供质量背书 |
| [DVC：Versioning Data and Models](https://doc.dvc.org/example-scenarios/versioning-data-and-models) | 数据／模型版本通过元数据与Git提交关联，可回溯、恢复和复现对应输入 | 交付固定成员、来源和规则的版本，而非用可变字段在下载时重新计算。这里只借鉴版本绑定原则，不安装DVC、不替换Oxen，也不把Oxen提交误称作Git内部实现 |

外部资料只用于上述结构和治理原则，没有上传任何真实样本、候选ID、包名／指令或私有路径作为搜索词。本段没有采用FAQ中的旧版本样本数量，也不将第三方基准的比例套成自有数据的行业标准。

## 当前真实数据仍是候选阶段

R12实现了同项目成员管理和发布能力；R14仅完成本机只读成员候选分析。现有四真实项目未因这份说明启用分组、复制项目或发布文件。敏感实体与Skill关键成员的交叠、未解析配对和有效独立复核为0的事实仍以[R14审计](real-dataset-split-candidates-r14.md)为准。选择了正确的存储方式，也不能消除候选中的内容泄漏或质量问题。

本次核对只读取工程源码／文档及公开官方网页。未读取真实样本正文或私有成员索引，未操作服务和Git；本文不是新的UI、容量、浏览器下载或真实分层发布验收记录。
